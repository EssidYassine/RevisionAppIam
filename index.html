Core Definition

IAM

Framework of policies, technologies, processes & programs to manage digital identities and govern user access.
Core principle: Right identity → right access → right resource → right time.

Identity — 3 Data Types

  • Identifiers — unique labels: employee ID, username
  • Credentials — proof of identity: password, certificate, SAML assertion, biometric
  • Attributes — descriptive info: name, role, department
4 IAM Pillars

1 Identification

Claiming an identity. Requirements: Unique · Non-descriptive · Secure assurance

2 Authentication

Type I — Knowledge: password, PIN, OTP, passphrase
Type II — Possession: token, smartcard, hardware key
Type III — Biometrics: fingerprint, iris, face
MFA — 2+ DIFFERENT factor types

3 Authorization

Need-to-Know · Least Privilege · SoD · Default to Zero · Implicit Deny · ACL

4 Accountability

Auditing & logging. Each entry: Identity + Action + Object + Timestamp. Logs retained 1 year. No overwrite.

Kerberos — Architecture & Flow

Components

  • KDC = AS + TGS, runs on Domain Controller
  • AS → verifies credentials → issues TGT (encrypted with TGS secret key)
  • TGS → validates TGT → issues Service Ticket ST (encrypted with service secret key)

6 Steps

1. Client→AS: Request TGT
→
2. AS→Client: TGT + Session Key
→
3. Client→TGS: Request ST + TGT
→
4. TGS→Client: ST + Session Key
→
5. Client→Server: Request + ST
→
6. Server→Client: Access Granted
KDC = Single Point of Failure. Compromised → all secret keys exposed. Offline → no auth possible.
Kerberos Attacks

🔴 Kerberoasting

Request TGTs for SPN accounts → crack hashes offline. Tools: Mimikatz, Rubeus.

🔴 Golden Ticket

Forge TGT with stolen krbtgt key → admin access to ALL services. KDC auto-trusts it.

🔴 Silver Ticket

Forge ST from cracked computer account → access ONE service. No KDC contact (stealthier).

🔴 Pass-the-Ticket

Replay stolen TGT/ST to impersonate a user — no password needed.

SAML SP-Initiated Flow
1. User hits SP resource → SP detects unauthenticated
2. SP redirects to IdP with SAML AuthnRequest
3. User authenticates at IdP
4. IdP generates & signs SAML Assertion (XML)
5. IdP sends SAML Response to SP's ACS URL via browser
6. SP verifies signature → grants access
